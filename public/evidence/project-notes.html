DocChat: choosing a retrieval default

The larger retrieval comparison used 127 questions over 781 chunks from 14 sources. Both configurations ran through the production retriever. The existing default uses dense retrieval plus a lexical overlap reranker; the alternative combines dense and BM25 rankings with reciprocal rank fusion.

Production retrieval comparison · same 127 questions
ConfigurationRecall@1MRR
Dense + overlap0.6930.834
Hybrid BM25 + RRF0.5830.761

Hybrid minus default MRR: −0.073, with a 95% paired-bootstrap interval of −0.114 to −0.035 (10,000 resamples). The decision rule required hybrid to be at least as good on Recall@1 and MRR and better on Recall@5 before changing the default. It failed that rule, so the default stayed dense.

Interpretation limits

MRR measures where the first relevant result appears, not generated-answer correctness. The set retains 24 original development questions and adds 103 LLM-generated questions. Labels were not independently audited. This supports an engineering decision on this dataset, not a general claim about unseen documents.

JobFit: a recoverable application workflow

The implementation uses six specialist agents in two phases: job parser, match scorer and gap analyst, followed by resource planner, cover letter and resume tailorer. Outputs are validated, results persist, progress streams to the UI, and failed or missing stages can be retried under a database lock.

Cost records capture model, tokens, cost and latency per call. The cost-report script compares recorded usage with an all-Sonnet counterfactual. No fixed percentage saving is asserted here because a supporting run export was not available in this review.

Evaluation and deployment status

The documented deterministic evaluations use mocked fixture outputs and validate contracts, not model performance. The live evaluation results are marked “not yet run.” The README describes Railway deployment; AWS task definitions remain in the repository, but the AWS environment is shut down. Deployment availability was not tested for this portfolio update.

SuperOps: deterministic tools behind a conversational interface

Store identity comes from the verified chat. The model chooses scoped tools; code calculates money in integer paise. Finalizing a bill locks relevant rows and updates inventory and customer credit in one transaction. Repeated calls are handled with idempotency keys.

The repository documents keyless replay checks and synthetic safety cases that call registered tools and assert database state. These checks provide evidence about tool behavior; they do not measure a live model's ability to choose the right tools.

Limits

No accepted live-agent baseline is claimed. A replay that takes a different tool path can exceed the current ordinal-key idempotency design. Inter-state GST, partial returns and several other retail cases remain outside the implementation. The Telegram bot is invite-only; no public demo access is promised.
